+++\ntitle = "How I built this portfolio ground up (TLDR)"\nslug = "building-blog-with-zola-ground-up"\ndate = "2026-02-22"\n+++\n\n<img style="width: 100vw;" width="1600" height="900" src="https://d3bphourhbt2ew.cloudfront.net/images/brown-leaf.jpg" />\n\n## Introduction\n\nHi readers. In this article, I would like to show the process I took for building & publishing this website (https://yella.dev). But before that, let's see some background.\n\n## Goal\n\nTo build a personal website with blog posts written in Markdown & Text-to-speech features like "Listen". The content should be committed & pushed to GitHub which should be automatically deployed.\n\n## Why I created this custom portfolio website?\n\nI designed & deployed this website to create a clean space to host my portfolio and writings. I've tried popular platforms like WordPress, Medium & Substack but didn't like their customization options to reflect my personal taste. Therefore, I decided to create a new portfolio that lists my projects, books & writings in one single place, and this website is the answer.\n\nI bought my domain (yella.dev) on Namecheap Domain Seller. Word `Yella` is a prefix of my last name: Yellavula.\n\n## Options for static site generation\n\nI shortlisted a few static site generators like Pelican (Python), Astro Docs (JavaScript), Hugo (Go), Zola (Rust). I finally picked Zola & discarded the rest for my portfolio due to the reasons below:  \n\n### 1. Pelican - Python ❌\n\nI previously used [Pelican](https://getpelican.com/) static site generator before and wanted to try something modern this time.\n\n### 2. Astro Docs - JS ❌\n\nI am not a big fan of JavaScript tools due to so many NPM dependencies & security vulnerabilities. Also, I want to keep static site generation & builds as separate technologies. Therefore I skipped [Astro Docs](https://astro.build/)\n\n### 3. Hugo - Go ❌\n\n[Hugo](https://gohugo.io/) is a great static site generator tool, but complex and has a steep learning curve. My goal is to get started as fast as possible, and picking Hugo wouldn't help my purpose.\n\n### 4. Zola - Rust ✅\n\nZola is the latest static site generator of all which combines both performance and simplicity. After taking a look at the GitHub project, I am convinced this is the fastest way to write in Markdown & build a static site. Zola also has a modern set of themes, and I liked a theme called "Oceanic Zen" for my blog & website.\n\n## Initial Setup with Zola\n\nI created my project by first installing zola on macOS:\n\n```sh\nbrew install zola\n```\n\nOnce installed, I initialized a Zola project using the "init" command:\n\n```sh\nzola init yella.dev\n```\n\nThis creates a directory called yella.dev and places necessary files like the `content` directory and `config.toml`. You can see Zola directory structure here: [Zola Directories](https://www.getzola.org/documentation/getting-started/directory-structure/)\n\nZola uses "Sass" extension language for Cascading Style Sheets (CSS) making it easier to build styles and reuse them. The file: config.toml controls how Zola builds the website. For a full list of available options, refer here: [Zola Configuration](https://www.getzola.org/documentation/getting-started/configuration/)\n\n## Picking Oceanic Zen theme for look & feel\n\nZola has a wide variety of themes covering different use cases (blog, docs etc.) here: [Zola themes](https://www.getzola.org/themes/)\n\nI picked Oceanic Zen due to its minimalism and clean layout.\nI vendored the theme from GitHub and copied it into the "themes/" directory in the project. I adjusted the font, font-size and colors based on my taste.\n\n## Next step: Deploying the website\n\nOnce the content is ready in the content folder and other tweaks with the theme & custom font are done, now is the time to deploy the website.\n\nI used various Amazon Web Services (AWS) to deploy my website end-to-end (E2E). The services I leveraged in the process are: \n\n1. AWS Amplify - For hosting the Zola build contents (public/ directory)\n2. Amazon Simple Storage Service (S3) - For storing website images & binaries (MP3)\n3. Amazon CloudFront - For delivering S3 contents securely\n4. Amazon Route 53 - For connecting custom domain (yella.dev) to Amplify app\n5. Amazon IAM - For creating service accounts to access S3 & CloudFront distribution. This is needed for GitHub integration.\n\n## Deployment Architecture\n\nThe architecture has four main phases: \n\n1. Publishing phase (For writing blog articles)\n2. Text to speech conversion phase (for converting articles into listenable audio)\n3. Delivery phase (to deploy the update)\n4. Cache invalidation phase (to reset audio & static files)\n\nThese four phases are divided into five partitions as shown in the below flow diagram.\n\n<img style="width: 100vw;" width="1600" height="900" src="https://d3bphourhbt2ew.cloudfront.net/images/arch.png" />\n\nThe architecture is straightforward with separation of responsibility handled by different entities. For example, publishing happens locally and is then pushed to the GitHub repository.\nA GitHub CI workflow extracts text from a new article, converts it into audio using OpenAI Whisper API, then uploads it to S3. Finally, there is a cache invalidation step that resets the blog static assets like images and audio to serve fresh content. This invalidates all content at the moment, but can be optimized further.\n\nAs AWS Amplify is already listening to the repository changes, it automatically syncs changes from the repo into the Amplify app. This is how the blog content gets deployed.\nThe custom domain (yella.dev) is connected with Amplify via Route53 A & CNAME records for yella.dev, www.yella.dev respectively.\n\n## Security Considerations\n\nThere are multiple security aspects considered during the development.\n\n1. All secrets are stored in encrypted GitHub secrets. Can be improved by migrating them to AWS Secrets Manager\n2. To upload audio to S3 and for invalidating cache, an IAM OIDC trust relationship with required permissions is set up between the GitHub repository & AWS CloudFront distribution with the least-privilege principle.\n    ```json\n    {\n        "Version": "2012-10-17",\n        "Statement": [\n            {\n                "Sid": "CloudFrontInvalidate",\n                "Effect": "Allow",\n                "Action": [\n                    "cloudfront:ListInvalidations",\n                    "cloudfront:CreateInvalidation"\n                ],\n                "Resource": [\n                    "arn:aws:cloudfront::REDATCED:distribution/REDATCED"\n                ],\n                "Condition": {\n                    "StringEquals": {\n                        "aws:PrincipalAccount": "REDATCED"\n                    }\n                }\n            },\n            {\n                "Sid": "S3UploadAudio",\n                "Effect": "Allow",\n                "Action": [\n                    "s3:PutObject",\n                    "s3:AbortMultipartUpload",\n                    "s3:ListBucket"\n                ],\n                "Resource": [\n                    "arn:aws:s3:::yella-blog-assets",\n                    "arn:aws:s3:::yella-blog-assets/audio/*"\n                ],\n                "Condition": {\n                    "StringEquals": {\n                        "aws:PrincipalAccount": "REDATCED"\n                    }\n                }\n            }\n        ]\n    }\n    ```\n3. The source code is scanned with a SAST tool like Semgrep to make sure code is free from supply-chain vulnerabilities.\n4. Add Web Application Firewall (WAF) for both Amplify App (blog content) & CloudFront distribution (blog static assets) to protect from bots & common attacks\n\n<img style="width: 100vw;" width="1600" height="900" src="https://d3bphourhbt2ew.cloudfront.net/images/amplify-waf.png" />\nMake sure to toggle these settings ON on Amplify Firewall:\n\n1. Enable Amplify-recommended Firewall protection\n2. Restrict access to amplifyapp.com\n\n## Conclusion\n\nBuilding a website using a platform like Vercel or Netlify can be easy but it overlooks a lot of options like customization, and security.
